A GPU actor, step by step

Twenty-five steps from a bare machine to a container running nvidia-smi on a real Tesla T4 — then suspending it, freeing the card, and giving it back. Every command and every number here was taken off hardware.

micro-VM  ·  cloud-hypervisor v52  ·  Tesla T4  ·  measured 2026-08-12

The cast, before we start

VFIO
A Linux facility that lets a normal userspace program own a physical PCI card. vfio-pci is a stub driver whose whole job is to claim the card so that nothing else can, and then hand it to whoever asks. It is how a VM gets real hardware.
IOMMU
Hardware that acts as a page table for devices. A GPU writes to memory on its own; the IOMMU constrains it so it can only reach one VM's pages. This is what makes handing real hardware to untrusted code safe.
cloud-hypervisor
The VM monitor. An ordinary Linux process that happens to be running a guest. Driven over a REST socket.
atelet
Our per-node agent, a DaemonSet. Builds bundles, stages snapshots, calls into the worker.
ateom
The privileged container inside each worker Pod. It launches cloud-hypervisor itself — there is no kata-runtime and no containerd shim anywhere in this path.
NVRC
NVIDIA's init. PID 1 inside the guest. Brings up the driver, then hands off.
kata-agent
Stock, unmodified. The thing inside the guest that actually creates your container.
CDI
Container Device Interface — a spec file saying "to give a container this GPU, create these device nodes and mount these libraries". Someone writes it; someone else applies it.
Phase one

Before any actor exists

Three things happen at node setup. After them, the machine has a GPU that the host itself cannot use — which is exactly what we want.

01
node boot

The machine boots with the IOMMU switched on

Without an IOMMU the kernel will not let a userspace process take ownership of a PCI device, because it would have no way to stop that device writing anywhere in memory. Passthrough is simply unavailable.

# /etc/default/grub GRUB_CMDLINE_LINUX_DEFAULT="... intel_iommu=on iommu=pt"
Also: the host kernel must be 6.5 or newer. We mount the container rootfs overlay using lowerdir+, which does not exist before then. Ubuntu 22.04 needs its HWE kernel (6.8) for this.
02
nvidia-vfio-manager

The GPU operator takes the card away from the host

Running in vm-passthrough mode, the operator binds each GPU to vfio-pci. It deliberately does not deploy the usual driver DaemonSet.

$ lspci -nnk -s 0000:da:00.0 NVIDIA Corporation TU104GL [Tesla T4] Kernel driver in use: vfio-pci
The host now has no NVIDIA driver at all. No nvidia.ko, no nvidia-smi. If you ssh to the node and try to look at the GPU, you will find nothing. That is not a misconfiguration — it is the design.
03
sandbox-device-plugin

The card is advertised to Kubernetes under a model-specific name

Not nvidia.com/gpu. In passthrough mode the resource carries the actual model, because you are being given one specific physical card rather than a slice of a shared one.

$ kubectl get node -o jsonpath='{.status.allocatable}' nvidia.com/TU104GL_TESLA_T4: "1"
Worth remembering: nvidia.com/gpu is the time-slicing name and never appears in this mode. Asking for it gets you a pod that will not schedule.
Phase two

Starting the actor

From your request to a booted VM with the card already inside it.

04
you

You ask for an actor with a GPU

The request names the model-specific resource from step 3.

# WorkerPool template: resources: nvidia.com/TU104GL_TESLA_T4: 1
05
atecontroller

That becomes a worker Pod

One Pod per actor. Inside it, a single privileged container named ateom. It is scheduled onto a node carrying the label ate.dev/sandboxClass=microvm — nothing else sets that label, so it is the only thing steering placement.

06
kubelet

Kubernetes tells the pod which physical card it got

The device plugin sets an environment variable naming the PCI address. This is the moment an abstract resource request becomes a specific piece of silicon.

PCI_RESOURCE_NVIDIA_COM_TU104GL_TESLA_T4=0000:da:00.0
Why we read the environment rather than scanning the system: ateom is privileged, so if it enumerated /dev/vfio it would see every GPU on the node and happily assign all of them to this one actor. The environment variable is the only authoritative statement of what this pod was actually allocated.
07
atelet

The node agent builds the bundle and calls the worker

atelet assembles the OCI bundle and the runtime assets, then makes a gRPC call into the pod.

atelet ──RunWorkload──▶ ateom
08
ateom

The VM is created with the GPU already attached

The BDF from step 6 is turned into a device path and passed in at VM creation time, before the guest has run a single instruction.

# resolveWorkerDevices() → { "path": "/sys/bus/pci/devices/0000:da:00.0/" } POST /api/v1/vm.create # devices included here POST /api/v1/vm.boot
This is cold-plug, not hot-plug — and it is load-bearing. Remember it; step 21 is entirely about the fact that a card added later behaves differently from one that was present at boot.
Phase three

Getting the GPU into your container

The guest boots, discovers the card, and works out how to expose it. Almost all of this happens inside the VM — the host contributes one line of text.

09
NVRC · guest PID 1

The guest loads the NVIDIA driver

NVRC is NVIDIA's own init, and it is the first thing that runs. It loads driver 595 — baked into the guest rootfs — and starts nvidia-persistenced.

So here is where the driver actually lives: in the guest kernel. The host has vfio-pci and nothing else. The real driver is talking to the real silicon; it just happens to be doing so from inside a VM.
10
NVRC

NVRC writes the CDI spec, then becomes kata-agent

Before it hands over, NVRC generates the file describing how to give a container this GPU, and blocks until that is done.

$ nvidia-ctk cdi generate --output=/var/run/cdi/nvidia.yaml $ exec kata-agent
Because the spec is generated inside the guest, its device numbers are already guest-native. There is no host-to-guest translation step anywhere in the codebase, and there does not need to be. It also runs exactly once, at boot — which is the second reason cold-plug matters.
11
ateom

The host adds one annotation — and touches nothing else

This is the entire host-side contribution to getting a GPU into your container.

cdi.k8s.io/ate-passthrough = nvidia.com/gpu=all
It strips inherited cdi.k8s.io/ annotations first. Those name host-side CDI devices, which do not exist inside the guest — and an unresolvable CDI device does not get skipped, it fails CreateContainer outright. It also checks the device really is a display-class NVIDIA GPU, so the HDMI-audio function sharing the IOMMU group does not get annotated, and neither does an unrelated passthrough NIC.
12
kata-agent

The agent does the actual injection

On CreateContainer it reads the annotation, resolves it against NVRC's spec, and creates the device nodes, mounts the driver libraries, and writes the device-cgroup entries.

# observed inside the actor 195:0 /dev/nvidia0 195:255 /dev/nvidiactl 239:0 /dev/nvidia-uvm
Nothing in our code writes these. They are the agent's work, using numbers that only make sense inside this guest.
13
your container

The GPU is there

Your image is unmodified. From inside, this is indistinguishable from a bare-metal machine with a T4 in it.

$ nvidia-smi Tesla T4 · driver 595
Phase four

Suspending — giving the card back

A snapshot can record guest memory and CPU registers. It cannot record what is inside a GPU. So before we take one, the card has to leave.

14
ateapi

A suspend is requested

From you or from a controller. The chain is always the same, and no controller ever talks to the VM monitor directly.

kubectl-ate │ atecontroller ─▶ ateapi ─▶ atelet ─▶ ateom ─▶ cloud-hypervisor
15
ateom

First: does this worker even have a device?

The check happens before anything is asked of the VM monitor, so an actor without a GPU pays nothing at all for this machinery existing.

16
inside your container

Turn persistence mode off

This has to happen before anything else, and it has to happen inside the guest.

$ nvidia-smi -pm 0
With persistence on, the driver holds a reference to the card indefinitely. The kernel's PCI remove callback sits in a loop waiting for that reference count to reach zero, and it never does. The eject would hang forever.
Why "inside your container" and not "inside the guest": the guest has no shell — busybox only, no /bin/sh. Every question we ask the guest has to be executed inside a container via the agent. That one constraint shapes a surprising amount of this design.
17
ateom

Ask the VM monitor to eject the card

POST /api/v1/vm.remove-device { "id": "_vfio4" }
The id is auto-assigned from a counter that is global across all devices, so the first passthrough device is not reliably _vfio0. We have watched it go _vfio3 → _vfio4 across a single cycle. It has to be read back, never assumed.
18
ateom

Wait for the eject to genuinely finish

Two independent signals both have to clear: the device id leaving the VM's device tree, and the monitor's /dev/vfio/<group> file descriptor disappearing from its open files.

measured 1.68 s
Why two signals: cloud-hypervisor clears its own config the instant an eject is requested — which is precisely the window this check exists to observe. Trusting the config alone would report success while the card was still attached.
19
ateom

Refuse to snapshot if the card is somehow still attached

A last gate before the point of no return.

This one is nasty. The VM monitor's passthrough device has an empty pause implementation. So vm.pause stops the virtual CPUs, but a bus-mastering GPU carries on writing into the very memory being serialised. You get a torn snapshot — and the monitor reports success. The only defence is refusing to start.
20
cloud-hypervisor

Pause, then snapshot

Guest RAM and vCPU registers go to disk. No GPU state — none of it was ever readable.

POST /api/v1/vm.pause POST /api/v1/vm.snapshot
The card is now free. Another actor can be given it while this one sits on disk. That is the entire point of the exercise.
Phase five

Resuming — taking it back

Not simply the reverse. Two things have to be done differently, and both were discovered on hardware rather than predicted.

21
ateom

Restore the memory eagerly, not on demand

Ordinary actors page their memory back lazily as it is touched. Any actor with a passthrough device is forced to copy all of it up front.

eager ≈ 1.6 sordinary actor: 164–676 ms
VFIO has to pin guest memory to map it into the IOMMU, and pages backed by lazy fault handling cannot be pinned. Get this wrong and the attach in the next step fails with VfioDmaMap(IommuDmaMap(Error(14))).
22
ateom

Attach the card before resuming the guest

POST /api/v1/vm.add-device { "path": "/sys/bus/pci/devices/0000:da:00.0/" }
measured 0.65 s
Order matters: a running guest will process the hot-plug event before the monitor has finished mapping the new memory windows, and the device comes up wrong.
The address comes from the worker's current allocation, never from the snapshot. An actor can resume on a different machine, where the same model of card sits at a different PCI address.
23
cloud-hypervisor

Resume the guest

POST /api/v1/vm.resume
24
inside your container

Check the GPU — and re-probe the driver if it did not come back

One nvidia-smi -L. If it fails, the driver is unbound and rebound by writing the guest's PCI address into sysfs, then polled until it answers.

$ echo <bdf> > /sys/bus/pci/drivers/nvidia/unbind $ echo <bdf> > /sys/bus/pci/drivers/nvidia/bind
This step is the one the design did not anticipate. The guest's own hot-plug probe fails: it assigns the memory windows and probes the card 14 milliseconds later, at which point the driver reports the GPU has no firmware processor and gives up — permanently. Writing to bind re-probes a card whose windows have since settled, and it binds the same GPU with the same UUID.
It is also why the actor gets /sys/bus/pci/drivers/nvidia bind-mounted writable over an otherwise read-only /sys. The capability granted is rebinding its own driver inside its own VM, which does not cross the isolation boundary.
25
your container

Back where we started

Same card, same UUID, same container image, memory restored.

GPU usable 5.8 s after attach total restore 9.02 s non-GPU actor: 164–676 ms
Where the time actually goes: roughly 6.7 of the 7.3 seconds of GPU overhead is the driver being probed twice — once by the failing hot-plug path, once by our rebind. The eager memory restore, which looks like the expensive part, costs about 1.6 s. If this gets optimised, that is the thing to attack.
Phase six

What this does not do

Stated plainly, because the failure mode is the interesting part of the design.

A busy GPU cannot be suspended — and it fails closed

If a CUDA context is still open, the driver will not release the card. The remove callback blocks, the eject wait times out, the detach returns an error, and the snapshot is refused. Nothing is corrupted; the suspend simply does not happen. We cannot suspend a GPU mid-computation, and we would rather say so than produce a snapshot that silently does not work.

  • Idle GPUs only. The card must be quiescent at suspend time. cuda-checkpoint would be the way to lift this, and is not implemented.
  • Multi-GPU is untested. The code paths handle N>1 and the annotation says all, but no actor with more than one card has ever been exercised on hardware.
  • Cold-plug at boot is required. NVRC writes the CDI spec exactly once. A card hot-added to a VM that booted without one would never appear in that spec, so the container would get no injection.
